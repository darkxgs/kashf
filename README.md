# Kashf (كشف)

A free check-up for online stores. Paste a store's address and Kashf opens it the way a shopper's phone does, runs 51 checks across speed, search, trust, mobile and Arabic support, and security, then writes a prescription: the five fixes worth making first, in plain Arabic or English, with steps for the store's platform where they differ.

*Kashf* is the Arabic word for a doctor's examination. The report reads like one: a score out of 100, a vital sign per area, and *الروشتة*, the prescription.

**Try it** on the built-in demo store: a fictional perfume shop, Naseem, built with mistakes on purpose (render-blocking scripts, a 2 MB PNG hero, two H1s, a product schema with no price, broken footer links), so the report always has something real to find.

## What a check-up covers

| Area | Weight | What Kashf looks at |
|---|---|---|
| Speed | 25% | Server response time, total page weight, images over 300 KB, WebP/AVIF use, scripts that block the first paint, compression, HTML size, lazy loading, image dimensions (layout shift), third-party scripts, browser caching. Plus Google's Lighthouse mobile score when PageSpeed Insights answers in time. |
| Search | 25% | Indexable (meta robots and `X-Robots-Tag`), content visible without JavaScript, title, description, H1, alt text, link previews (Open Graph), robots.txt, sitemap, canonical, structured data, Product schema with a price, hreflang, favicon. |
| Trust | 25% | HTTPS, the http→https redirect, certificate expiry, a phone/email/WhatsApp link, return, shipping and privacy policies, payment methods shown (mada, Apple Pay, Tabby, Tamara, valU, Fawry, cash on delivery…), commercial registration or VAT number, social links, broken internal links, a visible price and an add-to-cart button on a product page. |
| Mobile and Arabic | 15% | Viewport, zoom not disabled, Arabic text laid out right to left, a declared page language, a home-screen icon, and whether an Arabic version exists at all. |
| Security | 10% | HSTS, mixed content, `nosniff`, framing protection, referrer policy, and servers that announce their software version. |

Every finding has a title that states the result ("3 images are larger than 300 KB; the biggest is 1.7 MB"), why it matters to a shop, and how to fix it. Nothing is generated by a language model: each line comes from something Kashf measured or read on the page.

## How a check-up runs

1. **The page.** Fetched with a mobile Chrome user agent (tagged `KashfAudit/1.0`), following up to five redirects by hand. Kashf measures time to first byte and decodes Brotli and gzip itself, so it knows both the bytes on the wire and the size of the HTML. Bot-protection challenge pages (Cloudflare, PerimeterX, Akamai) are recognised and reported as "this store blocks automated checks" instead of being scored as a broken page.
2. **Security.** Reads the TLS certificate directly from the socket and tries `http://` to see whether it redirects.
3. **Assets.** Measures up to 30 images, 25 scripts, 12 stylesheets and 6 fonts, eight at a time: transferred size, real content type (an image served as WebP to browsers that ask for it counts as WebP), and cache lifetime.
4. **Crawl.** robots.txt (parsed with Google's rules: the longest matching pattern wins, `Allow` wins a tie, `*` and `$` supported), the sitemap it names or `/sitemap.xml`, the favicon, and 25 internal links for broken ones (HEAD first, GET when a server refuses HEAD).
5. **A product page.** Found by the URL shapes stores use (`/products/…`, `/p/…`, Salla's `/p123456`…), then read for a price, an add-to-cart button and Product structured data.

The page shows each stage as it finishes. The report is scored when the last one is done, and rescored if Google's PageSpeed result arrives later.

### Decisions worth reading

**Safe to point at any address.** A tool that fetches whatever URL a stranger types is a classic SSRF hole: `http://169.254.169.254/` or a hostname that resolves to `127.0.0.1` would let a visitor read the server's own network. Kashf checks the address every connection actually uses, inside undici's `lookup` hook, against loopback, private, link-local, CGNAT and IPv6 unique-local ranges. Because the check runs at connect time, it also covers every redirect hop and DNS rebinding, not just the address in the form.

**Returns before the work starts.** The form's server action writes an audit row and redirects straight to its report page; the audit itself runs in `after()`. Each finished stage is appended to a `jsonb` array (`steps = steps || $1`) that the page polls, so the progress list is the server's real progress. An audit that never finishes (a function killed mid-run) is marked failed the next time anyone opens it.

**Fixes in order of what they're worth.** The prescription ranks every failing or weak check by `weight × severity × area weight` and breaks ties by effort, so a quick fix outranks a developer job of equal value. Each item says how long the fix takes: a few minutes, an hour or two, or a developer.

**Arabic that agrees with its numbers.** Arabic counts change form with the number (صورة واحدة، صورتان، 3 صور، 11 صورة), so every counted phrase in the copy goes through a small `arCount` helper rather than a template with a number pasted in. Hosts and paths inside Arabic sentences are isolated with `<bdi>` so they don't reverse.

**Measurements are kept apart from conclusions.** Each audit stores what was measured (`facts`) separately from the findings and scores derived from it, and the checks are pure functions of those facts, which is also how they're tested.

**Private by default.** Reports are public to anyone with the link and aren't indexed. The rate limit (12 check-ups an hour per visitor) counts a keyed hash of the IP address, made with a random key kept in the database (or `RATE_SALT`), so the stored hashes can't be reversed by trying every address; the address itself is never stored. Checking the same store twice within two minutes reopens the running audit instead of starting another.

## Running it locally

```bash
npm install
npm run dev
```

Open http://localhost:3000. With no `DATABASE_URL`, Kashf creates an embedded Postgres in `.data/`. Under `next dev`, it is allowed to check localhost, so the demo store at `/demo-store` can be audited locally.

Settings are listed in [`.env.example`](.env.example). None are required to run locally.

## Tests

```bash
npm test
```

The tests start two small stores on a local HTTP server, one done well and one done badly (gzip, robots.txt, heavy images, missing tags), run the whole engine against them, and check the findings, the scoring, robots.txt matching, platform detection and Arabic counting.
